# /tako-read — 티켓 → 작업 요건 해석

이 커맨드의 가치는 한 가지: **티켓 본문을 "그래서 무엇을 해야 하는가"로 번역**한다. 작업을 *시작하기 전*에 쓰는 커맨드다. 조회 자체는 `tako show` 셸 명령이 책임진다.

## `/tako-check` 와의 경계

둘 다 티켓을 읽지만 시점과 질문이 다르다. 헷갈리면 사용자에게 어느 쪽인지 한 번 묻는다.

| | `/tako-read` | `/tako-check` |
|---|---|---|
| 시점 | 작업 **전** | 작업 **후** |
| 질문 | 이 티켓이 무엇을 요구하나 | 내가 한 작업이 요건을 충족하나 |
| 세션 맥락 | 없어도 됨 | **있어야** 의미 있음 |
| 결과물 | 요구사항 · 모호점 · 작업 분해 | 항목별 대조 · 누락 보고 |

사용자가 이미 작업을 한 상태에서 "이 티켓 봐줘" 라고 하면 `/tako-check` 쪽이 맞다.

## 작동 환경 가정

- `tako init` 으로 설정·인증 완료된 상태
- 세션 맥락은 **불필요**. 빈 디렉토리에서 호출해도 온전히 동작한다

## 흐름

### 1. 인자 정규화

사용자가 준 인자에서 이슈 키 추출:
- `WL-8876` 그대로
- `https://<site>/browse/WL-8876` URL 이면 키만 뽑기
- 인자가 아예 없으면 어떤 티켓인지 되묻기

### 2. 티켓 조회

```bash
tako show <KEY> --max-comments 20
```

`--json` 이 아니라 **기본 텍스트 출력**을 쓴다. 이유: 텍스트 경로만 본문·코멘트의 ADF 를 마크다운으로 변환해 준다. `--json` 은 Jira 원본이라 description 이 ADF 트리 그대로 실려 와 해석에 불리하다.

출력에 부모·하위 이슈·연결된 이슈·최근 코멘트가 함께 담긴다. 코멘트를 20개로 넉넉히 잡는 이유는 *요건이 본문이 아니라 코멘트에서 확정되는* 경우가 흔해서다.

조회 실패(404, 401, 403)면 셸 명령이 한국어 에러를 stderr 로 출력한다 — 그대로 사용자에게 노출하고 흐름 중단.

하위 이슈가 많은 에픽이면 상태별로 더 넓게 보는 게 낫다:

```bash
tako list --parent <KEY> --limit 50
```

### 3. 해석

읽은 내용을 다음 축으로 정리한다. **본문에 없는 것을 지어내지 않는다** — 없으면 없다고 쓴다.

- **요구사항** — 티켓이 명시적으로 요구하는 것. 원문 표현을 살리되 한 줄로 압축
- **완료 조건** — 무엇이 되면 끝인가. 명시가 없으면 "(명시 없음)" 이라고 적고 확인 필요 항목으로 넘긴다
- **제약** — 기한, 의존하는 티켓, 건드리면 안 되는 범위
- **모호한 지점** — 해석이 갈리는 문장, 빠진 정보
- **작업 분해** — 구현 관점 단계 제안. 티켓에 근거가 있는 범위까지만

부모·하위·연결 이슈는 *맥락*으로만 쓴다. 그 티켓들의 요구사항까지 이 티켓 것으로 합치지 않는다.

### 4. 보고

```
[KEY] 유형 — 제목 (상태)
링크: https://<site>/browse/<KEY>

## 한 줄 요약
이 티켓이 요구하는 것을 한 문장으로.

## 요구사항
- 항목 1
- 항목 2

## 완료 조건
- 항목 / 또는 (명시 없음)

## 제약 · 맥락
- 기한 / 의존 티켓 / 코멘트에서 확정된 결정

## 확인 필요
[모호] <해석이 갈리는 지점 — 무엇이 불분명한지>
[누락] <요건을 판단하려면 있어야 하는데 티켓에 없는 정보>

## 작업 분해 (제안)
1. 단계
2. 단계
```

빈 섹션은 통째로 뺀다. 확인 필요 항목이 없으면 그 섹션도 안 쓴다.

### 5. 마커 사용 규칙

- `[모호]` — 티켓에 쓰여는 있는데 해석이 둘 이상 가능
- `[누락]` — 판단 근거가 티켓에 아예 없음. 누구에게 물어야 하는지도 함께 (보고자 / 담당자)

이모지 안 씀. `[OK]` 계열 마커는 이 커맨드에서 안 쓴다 — 검증이 아니라 해석이라서.

## 의사결정 사전 상의 (반드시)

다음 상황에서는 추정하지 말고 사용자에게 먼저 묻는다:

- **티켓 본문이 한 줄이거나 비어 있음** — "본문이 거의 비어 있어 해석할 근거가 없습니다. 코멘트/부모 티켓까지 넓혀 볼까요, 아니면 보고자에게 확인이 필요할까요?"
- **요구사항이 여러 갈래** — 한 티켓에 서로 다른 작업이 섞여 있으면 어느 쪽을 먼저 볼지 확인
- **사용자가 곧바로 구현을 기대하는 눈치** — 이 커맨드는 해석까지다. 구현 착수는 사용자 확인을 받고 별도로
- **에픽·상위 티켓** — 하위가 여럿이면 "에픽 전체를 볼지, 특정 하위만 볼지" 한 번 확인

## 후속 요청

- "더 자세히" / "N번 항목만" → 해당 항목만 깊이 파서 추가 보고
- "이대로 작업 시작해줘" → 분해한 단계를 작업 계획으로 옮기고 사용자 확인 후 착수
- "다른 티켓도" → 추가 키 받아 같은 흐름 반복
- "작업 다 했으니 점검해줘" → `/tako-check <KEY>` 로 넘김

## 실패 처리

- `tako show` 가 비-제로 종료 → stderr 그대로 노출 후 중단
- 인증 실패(401/403) → `tako init` 으로 자격 증명 갱신 안내
- 키 형식은 맞는데 404 → 프로젝트 키 오타 또는 열람 권한 없는 프로젝트. 둘 다 가능성으로 제시

## 민감 정보 주의

티켓 본문·코멘트에 토큰·개인정보가 있을 수 있다. 이 커맨드는 그 내용을 세션 안으로 끌어온다 (v1.x 는 자동 필터링 없음). 민감 티켓에는 신중히 쓴다.
